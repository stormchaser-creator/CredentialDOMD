# Refund ticket upgrade

The original `20260930071000_limited_refund_support_tickets.sql` was amended after some installations had already applied it. Replaying the amended file alone adds a nullable standing column, so the next unchanged refund write can reopen an archived ticket and erase the operator's status. The new `20261001020000_upgrade_refund_support_tickets.sql` provides an additive upgrade without changing an installation's historical migration hash.

Apply the new file as one transaction, as the database owner, after the refund ledger and original support-ticket migrations exist. With psql use `-1 -v ON_ERROR_STOP=1`; a SQL-editor request must contain the whole file. It locks the refund ledger before tickets, stops only its own two triggers inside that transaction, backfills missing standings, removes untrusted reserved attribution markers, and installs the reviewed trigger and guard before releasing the locks. A failure rolls the whole change back. No account, payment, refund or support-message is created by the migration.

A linked legacy request establishes a baseline from its current refund state. A cancelled request remains unfinished while a retry holds a lease or has temporarily cleared its error. A linked request before cancellation already needed support. Existing non-null standings remain unchanged. This is a one-time baseline, not a claim that the old database recorded a complete history. Operator status, archive, resolution, approval, priority and ordering are preserved; later real standing changes reopen or resolve the existing ticket normally. A deleted ticket is not recreated. If an unsafe upgrade already erased an operator decision before this migration, the missing historical value cannot be inferred; this migration does not claim to recover it.

A genuine legacy ledger link proves ticket identity but cannot authenticate old editable wording. The upgrade clears reserved attribution on those legacy tickets, then regenerates subject, body and source from the ledger only where its current state is unambiguous. Other context is retained. An in-flight ambiguous state keeps its content without the Support label; a later authoritative restatement restores canonical text and attribution. A failed optional ticket write also leaves attribution absent. Unlinked or mismatched reserved markers are removed while member text and operator decisions remain. No ticket or conversation is inserted and no new-ticket notification is sent.

For a fresh database, apply the ordinary migration sequence including this additive file. For an existing database, retain the recorded hash of the version of 0710 it actually applied; do not rewrite that hash or pretend the amended file was applied. The local QA migration verifier may correctly flag the old/new 0710 difference after a source merge. Verify upgrades in a disposable fixture or a separately named fresh QA instance, or use a separately reviewed additive migration plan. Do not bypass the verifier or reset another running lab.

Rollback to the old behavior is refused because it would restore incorrect reopening and untrusted Support attribution. A correction must be a reviewed forward migration. This document is a local rollout plan; no production or shared lab deployment has occurred.

Validation: the populated legacy-schema regression uses the frozen earlier 0710 definition, demonstrates the amended-file failure in a rolled-back transaction, then applies the additive upgrade and checks operator preservation, concurrent retry standing, genuine later transitions, source authenticity, role isolation and idempotence. Only synthetic records and a private Unix-socket PostgreSQL cluster are used.
