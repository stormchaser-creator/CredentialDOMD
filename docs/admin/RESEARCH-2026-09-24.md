# CredentialDOMD administrative experience: research and prioritized changes

Research date: September 24, 2026. This assessment inspected `AGENTS.md`, `src/components/pages/AdminDashboard.jsx`, `src/lib/admin.js`, and selected administrative migrations in `/Users/ew/Projects/CredentialDOMD`. Findings refer to the starting source snapshot; implementation may subsequently change. Source review does not establish production deployment state.

The greatest immediate value is making administrative information trustworthy: complete counts, honest time periods, visible data failures, and controls that confirm actual server success. A richer visual dashboard built on the current capped arrays would make inaccurate answers more persuasive.

## 1. Fix demonstrated correctness problems first

| Priority | Observed gap | Recommended change and acceptance criterion |
| --- | --- | --- |
| P0 | The initial load caps tickets at 50, users/invites/leads at 500, errors at 50, and messages/proposals/attempts at 200. Tab badges and multiple summaries use array lengths. | Derive whole-population metrics in an authorized database query. Clearly distinguish total matching records from loaded rows. A fixture with more than each cap must produce correct totals. |
| P0 | `SignupsList` labels its sum “Last 90 days,” but its input comes from `admin_signups_daily.limit(30)`. | Query the full chosen date interval, independently of detail pagination. Define the timezone, include zero-activity days where useful, and return the interval in report metadata. A 90-day fixture with activity on 60 days must include all 60. |
| P0 | Failed visits, attempts, invitations, errors, and message reads are silently ignored. Other failures share one persistent error string. | Track loading/error/freshness per resource. A failed read must say “Unavailable” or “Could not refresh,” never masquerade as zero. Clear recovered errors, handle rejected promises, and support a targeted retry. |
| P0 | Invitation status/removal, lead removal, attempt dismissal, and field proposal status update local state before checking server success; several never inspect the result. ## 2. Establish a small reporting contract

Implement an admin-only report endpoint/RPC with a validated interval, generated timestamp, timezone, metric definitions, and source status. Summaries must come from full eligible datasets; paginated detail lists are separate. Database functions are appropriate for data-intensive operations; Supabase recommends invoker permissions by default, a fixed search path for a necessary definer function, and explicit execution privileges. [Supabase database functions](https://supabase.com/docs/guides/database/functions)

Recommended first reports, inferred from the application's existing workflows:

- **Operations:** unresolved tickets, urgent/high tickets, awaiting administrator response, waiting on member, awaiting agent approval, archived tickets, and oldest unresolved age. Current backlog is an as-of snapshot; newly created/resolved tickets are interval measures. Do not mix those denominators.
- **Accounts:** registered non-admin accounts, current access states, new accounts by day, and recent activity. Show incomplete setup as a support opportunity using the existing setup summary. “No recent activity” is an observation, not proof of abandonment.
- **Acquisition:** page loads, new accounts, waiting leads, guide-only requests, and invitations not yet accepted. Preserve the existing distinctions: views are not people, leads are not accounts, and a raw ratio of different populations is not a verified conversion rate.
- **Reliability:** error events and distinct error groups by build and date; distinguish current-build from other-build reports. Retained report counts are not historical incident totals when records can be deleted.
- **Administrative changes:** actor, action, target, timestamp, outcome, and reason for access changes. Reuse the lifetime-access audit model where appropriate.

Every report needs a drill-through to its filtered records, an explicit refresh control, and a clearly labeled export. Export the same filter and date interval shown, include generation metadata, and exclude secrets, raw session data, and unnecessary profile details. If text enters CSV, protect against formula injection and quote delimiters correctly; ordinary CSV quoting alone is insufficient, and spreadsheet behavior differs. [OWASP CSV injection](https://community.owasp.org/attacks/CSV_Injection)

## 3. Make controls authoritative and auditable

Keep administrative identity anchored to the existing server-verified `app_admins` relationship. Never reinstate email matching or trust an editable client value. Each read, export, and mutation must enforce permission at the server. Test unauthenticated, ordinary member, administrator, and revoked-administrator behavior. This follows deny-by-default and authorization on every request. [OWASP authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

New report views need explicit access design: Supabase documents that views commonly execute with their owner's privileges. Use an invoker view where suitable or a narrowly authorized function with grants and tests; do not assume table RLS automatically protects a newly exposed view. Preserve existing `current_profile_id()` identity semantics and inspect the latest migrations instead of copying old examples based on `auth.uid()`. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

For consequential actions, require the target and intended change to be explicit, record a short reason where useful, serialize conflicting operations, and write the successful mutation and audit receipt in one transaction. Capture actor identity server-side. An audit viewer should be read-only; routine browser roles should not alter its events. Exclude tokens, keys, passwords, and sensitive payload bodies from logs; sanitize event text and record a correlation ID for troubleshooting. [OWASP logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

## 4. Reduce administrative effort

The current tab click refetches all 11 datasets. Load the active workspace and the inexpensive global summary independently. Keep unaffected information visible while one resource retries. A summary can highlight actionable queues without forcing administrators to compare memorized numbers across tabs. GOV.UK supports tabs for frequent caseworking but cautions against slow hidden content and using tabs for information that must be compared. [GOV.UK tabs](https://design-system.service.gov.uk/components/tabs/)

Add search and practical filters to accounts and tickets: name/email, access state, status, priority, approval, and archive state. Apply filters server-side before pagination; otherwise “no results” may mean only “not in the first 500.” Use stable ordering with an ID tie-breaker and a visible result count. Supabase range pagination respects query ordering and uses inclusive bounds. [Supabase range](https://supabase.com/docs/reference/javascript/using-modifiers-range)

For large directories, use deliberate next/previous navigation with a clear current page and retained filters. Introduce pagination only when it improves performance or usability; avoid automatic infinite scroll for administrative records. [GOV.UK pagination](https://design-system.service.gov.uk/components/pagination/)

Use semantic tables for traffic and comparable report rows, with a caption, header cells, and associated data cells. Keep mobile access through an overflow container or an equivalent labeled detail layout. The current traffic report is visual CSS grid markup without table header relationships. [W3C accessible tables](https://www.w3.org/WAI/tutorials/tables/), [GOV.UK table](https://design-system.service.gov.uk/components/table/)

If retaining tabs, implement the complete tab pattern: tablist/tab/tabpanel roles, selected state, relationships, and arrow-key navigation. Native buttons should replace clickable divs where possible; ticket cards currently activate by Enter but lack Space behavior, and expandable error cards are click-only. Label inputs independently of placeholders and announce load/mutation outcomes. [W3C tab pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)

## 5. Policy boundaries and useful later work

The repository's approved policies remain part of the implementation: preserve the checkout pause, reviewed email holds, verified identity continuity, protected historical beta promises, approved lifetime grants, and billing checks for lifetime gifts. Legacy profile founding numbers must never be repurposed as the paid founding-place counter. No new reporting feature needs to charge, refund, grant access, send messages, or expose physician records as a test.

Later improvements should follow measured need: scoped support-versus-owner permissions when more administrators are added; report scheduling after report definitions stabilize; explicit incident resolution history; and provider-backed billing reconciliation only when current authoritative billing data can be verified. A physician credential tracker is not automatically a patient-record system, and this research makes no HIPAA or other regulatory certification claim.

## Release evidence

Before shipping, verify server authorization and report totals with a seeded database, including rows beyond current caps; confirm transactional rollback; test failed and delayed network responses; test stale-response handling after account/tab switches; review keyboard and mobile behavior; and run the existing relevant test suites plus the production build. Keep implementation, migration application, deployment, and live acceptance status distinct in the handoff.
